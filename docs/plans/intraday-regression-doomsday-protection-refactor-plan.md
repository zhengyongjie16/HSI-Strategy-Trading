# 日内回归策略末日保护内聚重构方案（二次复核版）

## 1. 状态、目标与结论

- 状态：设计方案，尚未实施业务代码迁移。
- 复核基线：Git `d5341d3`；下文行号对应此基线，实施时以函数名和实际调用链为准。
- 用户目标：将末日保护全部业务逻辑移入 `src/core/strategy/intradayRegression`，配置只在该目录的 `config.json` 定义，不再作为宿主独立功能，不允许通过全局环境变量定义。
- 结论：可行且合理，采用“策略独占业务政策、流程及状态；宿主保留中性执行能力和通用安全不变量”的边界。
- 置信度：现有调用链与业务边界高；未实施的并发行为必须由本文验收测试证明，静态复核不等于保证未来实现没有缺陷。

这不是目录搬迁或配置替换，而是一次跨策略契约、时间调度、交易授权、清仓协调和生命周期的职责迁移。不得保留宿主末日分支后仅通过改名宣称完成。

### 1.1 与既有策略方案的关系

本方案是以下文件的定向后续设计：

- `single-active-strategy-runtime-refactor-plan.md`：第 1.1、3、6.3、7 节中关于“策略只有普通意图、末日清仓归宿主”的边界。
- `single-active-strategy-runtime-execution-plan.md`：普通策略端口、末日专用路径及生命周期对应条款。

上述条款在本次迁移范围内由本文替代；其单活跃策略、免注册加载、静态 JSON、普通 emitter 白名单、启动提前校验、统一 fatal 和恢复安全约束继续有效。旧方案保留历史记录，不把旧边界误当成禁止执行用户本次需求的约束。

### 1.2 首要验收标准

1. 末日配置、时间规则、按日状态、撤单清仓协调、重试和专用错误恢复均属于 `intradayRegression`。
2. 宿主生产模块不导入该策略的内部末日文件，不读取末日配置，不包含 `DOOMSDAY_CLEARANCE`、`DOOMSDAY_WINDOW` 等末日专用分支。
3. 宿主只经中性策略契约消费策略政策，保留自身生命周期、交易日、连续时段、身份及订单事实安全检查。
4. 没有 K 线、报价事件时仍能进入窗口；不能以 `onCandlestick()` 驱动末日功能。
5. 原本受末日政策约束的最终订单副作用仍实时授权，不依赖最近一次时间事件更新的缓存布尔值。
6. 末日清仓不走普通智能平仓，也不转成保护性清仓。
7. `DOOMSDAY_PROTECTION` 出现在环境快照中即启动失败，包括空字符串；无兼容读取或静默忽略。
8. 切换到其他策略时，不自动继承本策略的末日保护。本文不建立所有策略强制日终清仓的系统政策。

### 1.3 非目标

- 不修改开盘保护、普通智能平仓、浮亏保护、保护性清仓冷却及损益分段。
- 不重建 SDK、限流器、行情接入、账户服务、订单跟踪与结算体系。
- 不扩大策略普通 emitter 的权限，不用 reason 文本识别清仓。
- 不新增多策略仲裁、通用插件注册框架或大型事件总线。
- 不将通用盯单、恢复撤单和超时补单改成依赖末日窗口的策略行为。
- 不承诺交易所一定成交或收盘前必然空仓；现有语义是安全提交可执行清仓需求，而不是成交保证。

## 2. 二次复核结论与修正

### 2.1 关键方案问题

本轮未确认新的现有程序运行时缺陷。以下是上一版方案表述不足会造成的迁移风险，必须在实施合同中修正。

- 静态配置先 prepare，再创建 SDK 和运行时：`app/runApp.ts:116–132`。
- 普通策略输出不授予清仓权限：`core/strategy/types.ts`、`businessEventProgram/emissionAdapter.ts`。

- 末日清仓已有专门的终态等待和新鲜可卖量处理，不应退回普通 SELL 路径。
- 已有末日、时间唤醒、最终 mutation 行情及策略配置行为测试，可作为迁移基线。

## 4. 必须保持的业务合同

### 4.1 时间和门禁

默认时间不变：

| 时段     | 正常日      | 半日市      | 行为                                 |
| -------- | ----------- | ----------- | ------------------------------------ |
| 拒买窗口 | 15:45–16:00 | 11:45–12:00 | 拒绝新买入，推进当日撤买检查         |
| 清仓接管 | 15:55–16:00 | 11:55–12:00 | 停止既有受约束普通业务，推进末日清仓 |
| 收盘后   | 16:00 起    | 12:00 起    | 不再推进末日订单动作或窗口重试       |

- 保留“窗口内”与“当日已达到买入截止起点”两种判断；现有 `hasReachedDoomsdayBuyCutoff` 用于最终买入授权，不能全部改成收盘前窗口布尔值。
- 15 分钟阶段不等于停止普通候选生成，也不等于停止正常卖出、浮亏风险或寻标；拒买仍在原轻检查和最终执行位置发生。
- 5 分钟阶段失效普通待验证候选，并阻断现有受末日接管约束的链路。
- 宿主开盘保护、生命周期、交易日和连续交易门禁继续独立生效。策略不能开放宿主已经关闭的权限。
- 实时授权必须使用当前时钟以及与当前香港日期匹配的日历事实。事实暂缺时不得假定正常交易日或正常收盘时间并放行；保留所属日历/生命周期链路的恢复责任。
- 启动或重建直接落在窗口内时立即补评估，不能只等待一个已经过去的边界。

### 4.2 撤买流程

- 按当前可证明席位集合查询待成交订单并筛选买单。
- 没有可归属席位不擅自标记当天完成。
- 没有待撤买单，或本轮结果已满足现有完成条件，才记录当日撤买检查完成。
- 请求接受/可信已结束/已成交/可重试失败/未知失败/尚未发起分别处理。
- 请求接受后，权威终态仍由订单系统推进；不得把 API 成功视为真实撤销终态。
- 部分未确认结果允许后续重评估，不把“每天一次”错误解释为全日最多发一次请求。
- 已完成标记按交易日隔离；进程重启后按恢复的真实订单再次评估，不新增未经要求的策略状态持久化协议。

### 4.3 清仓流程

1. 确认当前交易及策略授权有效。
2. 按当前席位和 pending switch 权威事实解析持仓归属。
3. 对无法归属的正可卖持仓 fail-fast，不静默忽略，不扩大成账户任意持仓清仓。
4. 获取并校验所需行情，区分缺失与无效。
5. 读取目标标的全部待成交卖单；按原协议撤单并记录等待的订单身份。
6. 等待权威终态必须以有限步骤返回 WAIT，不能持有一个无限等待成交/撤单的 Promise。
7. 终态收敛后重新读取真实可卖量；不把旧单原委托量、旧缓存持仓或终态数量缺失时的推测值当成新卖量。
8. 使用执行时行情与实时授权提交非保护性清仓卖单；不合并普通卖单、不调用智能平仓、不关联普通选单算法的 relatedBuyOrderIds。
9. 结果分类交还策略推进缓存处理或重试。每次重新推进都重新检查日、运行代际、席位方向/版本及订单事实。

等待期间不得重复撤销已经接受且尚未终结的同一订单。待终态集合属于策略私有状态，不再留在通用 submit flow。订单身份和终态仍由宿主订单系统负责；本地列表暂缺不能在缺乏对应不变量保证时被伪造成权威终态。

保持同标的既有订单 route 协作：新鲜数量执行能力不能绕过订单监控及原有事实检查。迁移不得因拆成多个 API 步骤，忽略期间出现的新待成交卖单或改变既有防重语义。

### 4.4 账务和缓存

- 末日卖单固定不带 `isProtectiveLiquidation: true`，不添加保护性备注，不产生保护性完成事件、清仓后冷却或损益分段切换。
- 当前完整提交成功后的账户缓存失效、对应持仓缓存投影移除、订阅协调和买单记录清理，见 `doomsdayProtection/index.ts:504–548`，按原条件迁移。
- 上述是当前的“提交后缓存投影”，不是交易所确认空仓。不能在文档或代码中改称已成交事实。
- 部分成功保留当前差异化处理，不能一律清空所有方向记录。
- 策略决定何时需要这些后处理，宿主提供最窄的缓存/账本操作能力，不注入可写 `LastState`。
- 已经发出的 SDK 请求即使晚于 stop 返回，也必须按宿主既有规则完成订单跟踪、成交事实或错误登记；不能因为策略 epoch 失效丢弃已产生的远端事实。

### 4.5 错误和重试

| 情况 | 处理合同 |
| --- | --- |
| 配置、身份、状态不变量、内部契约错误 | fail-fast，进入统一 fatal，不包装成外部失败 |
| 行情缺失 | 保留有限重试及耗尽集合，窗口外停止 |
| 行情无效 | 保留现有 readiness/outcome 所属阶段的拒绝语义；不得笼统当成缺失无限重试 |
| 待撤卖单尚无权威终态 | 返回 WAIT，记录目标身份和明确未来重评估 deadline |
| 明确外部暂态请求失败 | 由策略 owner 依配置安排重评估，不能游离 rejection |
| 提交结果不可确认 | 先保留/恢复订单与持仓事实，按现有流程刷新持仓和协调订阅，再决定未来重评估；禁止在同一步盲目重发 |
| 生命周期或窗口失效 | 停止新副作用，不恢复旧计划；保留宿主对已发请求的收口 |

重试计数、候选符号集合和耗尽符号集合沿用当前口径；不得顺便将当前批次重试预算改成每次事件/每个新任务重新获得完整预算。终态等待和 API 失败不能混算为行情缺失预算。

## 5. 目标架构与最小端口

### 5.1 策略内布局

```text
src/core/strategy/intradayRegression/
├── config.json
├── config.ts
├── definition.ts
├── index.ts
├── types.ts
└── doomsdayProtection/
    ├── index.ts
    ├── policy.ts
    ├── types.ts
    └── utils.ts
```

文件可按真实职责合并，但不能把所有新逻辑堆进已有 K 线处理函数。内部模块通过参数接收依赖，运行时类型和工具按仓库 TypeScript 规范组织；共享固定常量仍遵循仓库常量位置规则，业务可调参数放 JSON。

### 5.2 公共策略契约

在 `src/core/strategy/types.ts` 扩展中性能力；以下为职责合同，不是要求照抄的最终命名：

| 能力 | 同异步 | 约束 |
| --- | --- | --- |
| 读取当前策略政策 | 同步纯计算 | 输入当前时刻、有效日历及必要身份事实；不发 I/O，不靠最后一次事件缓存决定权限 |
| 接收时间/运行事实评估 | 同步 | 更新策略控制状态、失效普通 pending、排入私有业务工作，立即返回下一次未来唤醒时刻或 null |
| 启动/恢复运行会话 | 同步 | 绑定本次运行所需窄能力和代际；构造期不执行 I/O，不创建第二个策略实例 |
| 停止运行 | 同步 | 关闭接收、作废代际、撤销重试计划，不等待订单终态 |
| 排空已开始的有限工作 | 异步 | 等待本地 in-flight 收口；不等待下一次市场事件或未来定时器 |
| reset/destroy | 现有同步清理为主 | reset 在 drain 后调用；destroy 最终释放，不能成为唯一异步停止入口 |

所有必需端口更新 `createSelectedStrategy` 的运行时校验、测试策略与 fixtures。不能通过可选链掩盖未实现的新契约。

普通 `StrategyDecision` 和 emitter 继续只表达动作、时间与说明，不携带订单类型、数量、标的覆盖或绕过风险的自由字段。

### 5.3 授权不是一个笼统布尔值

公共政策应区分至少以下使用语义，不要求为每个消费者创建一套接口：

| 消费者 | 宿主基础条件 | 策略政策部分 |
| --- | --- | --- |
| 普通新评估 | 生命周期、连续时段、开盘保护、有效 origin | 是否允许普通业务新评估 |
| 普通即时/延迟回流 | 交易日、生命周期、连续时段、席位身份 | 是否允许普通业务回流；保持开盘保护现有差异 |
| 买入轻检查 | 原风险流水线及检查顺序 | 当前是否允许新买入 |
| 普通信号最终 submit/replace/cancel | 原生命周期、日期、时段及席位最终检查 | 当前普通命令/买入是否获准 |
| 浮亏风险、行情驱动换标/静态清仓 | 各自既有门禁及 freshness/席位检查 | 是否允许继续普通风险动作 |
| 自动寻标 | 生命周期、连续时段、既有寻标前提 | 当前是否获准；授权变更需要显式撤权通知 |
| pending switch route | 生命周期、连续时段、原 route 身份 | 区分接管 TERMINATE 与午休 PAUSE，不能混用 |
| 策略控制的撤买、清仓 | 通用身份、运行会话及最终执行约束 | 当前策略步骤是否仍有效，截止/清仓窗口由策略判断 |
| 恢复撤单、订单事实 route、追价、超时补单 | 原授权来源和原最终安全检查 | 不因本次迁移新增末日策略窗口限制 |

宿主生成执行身份，策略只在原有基础权限内施加自己的政策。不能通过 `reason`、任意 purpose 字符串或 `bypassRiskChecks` 布尔值让普通调用方获得清仓权限。

### 5.4 窄执行能力

策略运行上下文可以获得以下受控能力，而不是完整 `Trader`/`MonitorContext`/`LastState`：

- 读取不可变的当日、持仓、订单、席位及 pending switch 事实。
- 读取行情和 fresh 可卖量；事实来源与当前生产路径一致。
- 对指定订单身份请求撤单，结果保留接受、终态、失败、未开始等区分。
- 在受控策略会话下提交非保护性、按实时可卖量计算的卖出请求。
- 必要的账户缓存失效、持仓投影更新、买单记录清理与订阅协调。
- 发布中性的时间计划变化通知。

通用“按实时可卖量卖出”能力可以负责最终 quantity/quote/permit/track 的机械执行，但不得内藏末日窗口、按日标记、撤全部卖单状态机、末日重试预算或具体策略判断。先撤单并等待终态的业务顺序必须由策略拥有。

最终执行能力始终保留宿主自身校验，并实时回调策略授权；动作、方向、symbol、seatVersion、交易日及运行代际由明确契约绑定。不能把只允许卖出的端口做成通用任意 broker 请求透传。

## 6. 时间调度与异步协议

### 6.1 确定采用：单系统 timer + 同步策略时间钩子 + 私有异步协调器

不新增第二套末日定时器，不继续让系统 evaluator await 末日网络操作。

```text
系统 one-shot timer / 中性重评估请求
    ↓
系统时间评估（日历、生命周期、连续时段、开盘保护）
    ↓
同步策略时间钩子
    ├─ 计算当前政策、失效普通候选
    ├─ 向策略私有 single-flight owner 排入工作（不等待 I/O）
    └─ 返回下一次边界或 retry deadline
    ↓
发布完整授权变化，合并系统与策略未来时刻
    ↓
同一个系统 timer 重排

策略私有异步 owner
    ↓
有限业务步骤 → 执行结果/权威事实 → WAIT / DONE / RETRY
    ↓
仅在计划变化时通知系统重评估
```

时间钩子必须同步完成政策和候选失效，异步业务在当前同步控制阶段结束后才开始；授权事件应在可能产生新的策略订单副作用前发布。系统调用依然经过统一 fatal 边界。

### 6.2 计划和事件规则

1. 复用 `TimeWakeupRuntime` 的 single-flight/dirty-drain，窄化公开 `requestEvaluate()` 或等价中性端口，并同步修改类型。
2. 系统 planner 只处理策略返回的时间戳，不知道该时间是拒买还是清仓。
3. 策略返回未来的有限时刻或 null；已经到期的工作立即入私有 owner，不把过去时刻作为永久候选制造 busy loop。
4. 在异步步骤完成或明确失败后，若下一次 deadline 发生变化才通知；无变化结果不得形成“评估→任务→通知→评估”的空转循环。
5. 私有 owner 保留 in-flight 和 dirty。忙时的新唤醒标记 dirty，不直接丢弃；有限步骤退出后重读权威事实。
6. WAIT 必须绑定有效事件来源或未来 deadline。首版保留现有未来重评估 deadline 即可，不为追求纯事件形式强行扩展全量订单订阅。
7. 显式未来重试尚未到期时，其他无关重评估不得提前重复发请求、消耗次数或重置预算。
8. 完成的窗口动作不会因为“系统再次评估”就重放；协调器必须保留现有完成标记、已请求订单身份和耗尽状态。
9. 所有 retry deadline 按作出决定时的当前时钟计算，并裁剪到有效窗口内；不能沿用耗时 I/O 前的旧时间导致立即重试自旋。
10. 策略时间政策变化即使不改变 `canTrade`，也必须发布自动寻标完整授权变化。启动时首次值同样要发布，不能只监听连续时段布尔值。
11. 普通政策变化通知负责让 owner 及时失效；最终实时授权独立保证时间评估因外部查询或重建而迟到时不错误放行。

### 6.3 私有协调器状态

保留并明确管理：

- 当前运行代际与业务日期；
- 当日撤买完成标记；
- 是否已进入接管及普通候选失效状态；
- 当前有限步骤 in-flight/dirty；
- 待终态订单身份及目标标的；
- 行情重试计数、符号集合、耗尽集合及 deadline；
- 专用外部失败恢复阶段。

不要把“等待终态”实现成阻塞到订单成交的 await。先保存等待事实并结束当前步骤，后续事件/时刻重新推进。

异步 owner 自己捕获异常：外部暂态错误进入本策略重试逻辑；内部错误同步报告统一 fatal 并停止接收。系统 evaluator 不再 await 它之后，不能因此让错误成为未处理 Promise rejection。

## 7. 配置唯一来源

### 7.1 JSON 目标结构

保留 `signals`、`verification`，增加：

```json
{
  "doomsdayProtection": {
    "enabled": true,
    "buyCutoffMinutesBeforeClose": 15,
    "clearanceMinutesBeforeClose": 5,
    "orderType": "ELO",
    "retry": {
      "recheckIntervalMs": 2000,
      "quoteMaxAttempts": 5,
      "externalApiRetryIntervalMs": 1000
    }
  }
}
```

此处是新增块，不是完整配置文件。

参数依据：

- 启用默认 true、15/5 分钟来自当前全局开关和 `DOOMSDAY`。
- `orderType` 当前取 `global.tradingOrderType`，默认 ELO，**不是**全局 `liquidationOrderType` 默认 MO。部署迁移必须按该环境实际末日委托类型写 JSON，不盲目使用示例值。
- `recheckIntervalMs` 对应当前行情缺失、买单撤销复查及卖单终态等待所用 2000ms 间隔；不能误命名成只控制 quote 的参数。
- `quoteMaxAttempts` 对应当前五次延后重试预算，不包括初次尝试，保持 `resolveNextQuoteRetry` 口径。
- `externalApiRetryIntervalMs` 对应当前时间评估器用 `TRADING.INTERVAL_MS` 安排的 1000ms 外部失败恢复。迁移后只对该策略业务生效，宿主日历和生命周期仍保持自己的重试配置。

### 7.2 严格解析和范围

在 `intradayRegression/config.ts` 复用现有精确字段校验、同步 prepare 和递归冻结模式：

- 显式必填，拒绝 null、数组、未知字段、错误类型和非有限数值。
- `enabled` 为 boolean；关闭时也必须提供有效完整结构，无环境默认回退。
- 时间窗口为整数分钟，满足 `0 < clearanceMinutesBeforeClose <= buyCutoffMinutesBeforeClose <= 150`。150 来自当前支持的半日连续交易段 09:30–12:00，可保证参数不落入半日开盘前或正常日午休；不增加新交易日类型或任意跨时段窗口。
- `orderType` 复用当前配置支持的订单类型校验和映射，不能直接接受任意 SDK 枚举或字符串。
- 重评估/API 间隔为正安全整数，次数为非负安全整数；时间戳相加与 timer 安排必须通过有限有效时刻校验。0 次表示不做行情延后重试，不表示无限次。
- 构建后的配置为独立冻结对象，日志只在策略层输出自身摘要。

新增可调值在本次发布时全部使用原行为值；除明确将配置所有权迁移外，不顺便调参。

### 7.3 环境变量淘汰

- 删除全局读取、类型字段、validator 和配置日志。
- 使用 `LEGACY_STRATEGY_ENV_KEYS` 与 `prepareStrategy` 已有 presence 拒绝机制，新增 `DOOMSDAY_PROTECTION`。
- 对 app 合并后的完整环境快照进行检查；包括进程继承环境，不只是显式传入的参数。
- 不建立 JSON/环境变量优先级，不允许空值绕过，不根据当前选中策略静默接受旧键。
- 清理 `.env.example` 和 README 中相应的配置说明。
- 全局普通委托类型、保护清仓委托类型、宿主重试常量仍可服务原消费者，但不再影响该策略末日配置。

## 8. 生命周期、装配和停止顺序

### 8.1 启动

1. 读取完整环境，拒绝旧键。
2. 只 prepare 选中策略的静态 JSON，错误先于 SDK 初始化。
3. 创建唯一策略实例，登记 destroy；此时不得启动 timer、I/O 或 emitter。
4. 装配通用执行能力、日历、席位、订单、生命周期和系统 time runtime。
5. 绑定受控策略运行上下文。中性时间请求端口必须在运行开始前就绪；禁止未初始化 getter 静默返回允许或无操作。
6. 完成运行时快照和重建，建立订单跟踪及一致性 baseline。
7. 启动/恢复策略会话，由第一次系统时间评估补齐当前阶段，再启动允许放行的业务来源。

若重建失败，保持交易关闭和系统时间恢复链路运行；策略不能因为实例已创建而提前清仓。装配失败仍由统一 cleanup 释放已经登记的资源，不创建替代策略实例。

### 8.2 午夜和重建

- 先关闭宿主交易权限，策略同步 stop：关闭接收、撤销 epoch、清理未来计划。
- 保留订单事实系统对已经发出请求的收口能力，排空策略的有限 in-flight 工作。
- 随既有顺序排空其他交易 owner、停止订单监控及订阅，然后调用策略 `resetForTradingDay()`。
- 不在生命周期 tick 内调用系统 time runtime 的 `stopAndDrain()`；它必须继续推进午夜、开盘和失败重建。
- 新交易日全部基线重建成功后恢复策略会话，并立即请求一次系统评估。

现有 `signalRuntimeDomain.openRebuild()` 与初始启动是两条接线，都必须更新，不能只处理首次启动。

### 8.3 退出和 fatal

- `runApp` 的同步 `stopProducers` 加入策略运行 stop，不能仅保留 `invalidateAll()`。
- 全局退出可停止系统时间来源；策略 drain 必须安排在通用订单/行情能力销毁之前，destroy 在最终清理阶段。
- stop 后晚到的结果不能注册新 timer、恢复旧重试计划、继续提交下一张单或写回新运行代际的状态。
- 已产生的 broker 副作用仍按通用订单系统登记；策略取消不是远端订单自动取消。
- `invalidateAll()` 仍只清普通延迟候选。接管时调用它不能取消正在执行接管的末日协调器。
